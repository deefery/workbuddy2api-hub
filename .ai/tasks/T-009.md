## Outcome

Make the accepted NAS WorkBuddy2API deployment ready for safe off-LAN use through a dedicated Cloudflare Tunnel without giving relatives/agents tailnet or LAN reachability and without moving WorkBuddy's upstream egress away from the NAS.

The finished capability has two intentionally separate public surfaces:

1. `wb.zhijic.com` — owner/admin web management, protected by Cloudflare Access and then the existing panel password/session.
2. `wbapi.zhijic.com` — OpenAI/Anthropic-compatible API for relatives/clients, restricted to the approved `/v1` protocol endpoints and authenticated by WorkBuddy2API API keys.

`api.zhijic.com`, Tailscale, the existing LAN endpoint and the accepted WorkBuddy account/persistence state are not repurposed by this task.

## Current facts

- Accepted production image: `ghcr.io/deefery/workbuddy2api-hub:v1.7.2.1`.
- NAS deployment: `/share/Container/workbuddy2api-hub`, container `wb-proxy`, host/LAN `8788 -> 8788`.
- Persistent `accounts/` and `usage/` state has already survived down/up and force-recreate acceptance.
- T-008 keeps `wb-proxy` on its service-owned default network and also on `sub2api_sub2api-network`; OpenMAIC/Sub2API use Docker DNS `wb-proxy:8788`.
- The application already has a non-default panel password, API bearer-key enforcement, multiple independent API keys, key attribution and model restrictions.
- Management endpoints are panel-session protected, but `/` serves the dashboard shell; therefore the public API hostname must not simply publish the entire origin.
- `wb-proxy` accepts standard `/v1` OpenAI/Anthropic routes and also some bare-path aliases. The public API contract deliberately standardizes on `/v1` only.

## Approved architecture

```text
Owner browser
  -> https://wb.zhijic.com
  -> Cloudflare Access (deny by default; owner identity only)
  -> dedicated Cloudflare Tunnel
  -> wb-proxy:8788
  -> panel password/session

Relative / AI client
  -> https://wbapi.zhijic.com/v1/...
  -> Cloudflare edge protection
  -> dedicated Cloudflare Tunnel path allowlist
  -> wb-proxy:8788
  -> per-person WorkBuddy2API API key
  -> WorkBuddy (outbound still originates from NAS)
```

### Tunnel/runtime boundary

- Use a dedicated Cloudflare Tunnel for this service. Do not add WARP/private-network routes or bastion behavior.
- Run `cloudflared` as a separate NAS container/service, pinned to an explicit image version/digest at deployment time; do not use a floating production image unintentionally.
- Connect `cloudflared` and `wb-proxy` through a dedicated Docker network for this publication path. Preserve `wb-proxy`'s existing default network, `sub2api_sub2api-network`, host port, persistent mounts and service lifecycle.
- `cloudflared` must not receive the Docker socket, host networking, privileged mode, host filesystem mounts, or unrelated service networks. Use read-only/no-new-privileges/capability reduction where compatible with the official image.
- Tunnel credentials/tokens, Access identifiers and API keys stay outside Git/image layers. Version only templates/runbooks with placeholders.
- Do not add LAN CIDRs to the Tunnel configuration.

### Public API ingress allowlist

The API hostname should reach `wb-proxy` only for these paths (and the necessary HTTP methods/OPTIONS):

- `GET /v1/models`
- `POST /v1/chat/completions`
- `POST /v1/completions`
- `POST /v1/responses`
- `POST /v1/messages`
- `POST /v1/messages/count_tokens`

Use Cloudflare Tunnel hostname+path ingress matching where practical and finish with an explicit `http_status:404` catch-all. Do not expose the bare aliases (`/models`, `/responses`, `/messages`, etc.) on the public API hostname in this phase.

`/`, `/dashboard`, `/ui`, `/panel/*`, `/accounts*`, `/settings*`, `/usage*`, `/tasks*`, `/scheduler*`, `/logs*`, `/pricing*`, `/agents*`, `/health`, `/realm`, update endpoints and all unknown paths must not be forwarded by `wbapi.zhijic.com`.

### Management hostname

- `wb.zhijic.com` may route the complete web application because it is the management surface.
- Create a Cloudflare Access self-hosted application with deny-by-default policy and an explicit owner-only allow policy. Relatives are not members of this policy.
- Keep the application's panel password/session enabled as the inner control; Access does not replace it.
- Do not use URL/query-string panel/API credentials in public instructions.

### API identity

- Do not put interactive Cloudflare Access in front of `wbapi.zhijic.com`; standard SDKs/agents generally cannot complete its browser authentication flow.
- Use WorkBuddy2API API keys as the API identity. Create a separate key per person/client during authorized production setup, with meaningful non-secret labels and model/realm restrictions where appropriate.
- Client examples must use `Authorization: Bearer <key>` (or protocol-equivalent header for Anthropic clients). Do not recommend `?key=` / `?api_key=` public URLs.

### WAF / rate limiting

- WAF/rate limiting are edge safety controls, not authentication.
- A narrow custom WAF rule may enforce the API hostname/path contract as defense in depth, but Tunnel ingress is still expected to fail closed with a 404 catch-all.
- Do not use Managed Challenge/Interactive Challenge actions on the API protocol hostname.
- Avoid blindly applying body-signature WAF policy to LLM prompt payloads where legitimate source code/security text would cause false positives.
- Before creating rate limiting, inspect the current Cloudflare zone plan/capabilities. Current Cloudflare documentation indicates Free rate limiting can match only a narrower field set (notably Path rather than Host) while higher plans can scope by Host. Because `api.zhijic.com` also uses `/v1`, do **not** create a zone-wide `/v1/*` limiter if hostname scoping is unavailable.
- If hostname-scoped rate limiting is available, start conservatively and record the chosen rule/threshold in the handoff; it must tolerate normal agent bursts and shared-NAT family use. This is a coarse circuit breaker, not a billing/quota system.
