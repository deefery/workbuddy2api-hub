## Upgrade procedure

Before changing production, choose a reviewed/published exact fork release tag and record its expected RepoDigest.

On the NAS:

```sh
D=/share/CACHEDEV1_DATA/.qpkg/container-station/bin/docker
cd /share/Container/workbuddy2api-hub

# Snapshot persistent state before an upgrade. Keep this backup on the NAS and protect it as credential-bearing data.
ts=$(date +%Y%m%d-%H%M%S)
mkdir -p backups/$ts
cp .env docker-compose.yml backups/$ts/
cp -a data/accounts data/usage backups/$ts/

# Edit only WB_IMAGE_TAG to the reviewed exact tag, for example vX.Y.Z.N.
vi .env

$D compose pull wb-proxy
$D compose up -d
$D compose ps
curl -fsS http://127.0.0.1:8788/health
$D image inspect ghcr.io/deefery/workbuddy2api-hub:$(sed -n 's/^WB_IMAGE_TAG=//p' .env) --format '{{range .RepoDigests}}{{println .}}{{end}}'
```

Acceptance after upgrade must confirm the observed RepoDigest is the reviewed digest, container health is `healthy`, real accounts remain ready, and a minimal authenticated API smoke passes before the new version becomes the next baseline.

## Rollback procedure

If an upgrade fails and persistent-state format is still compatible:

```sh
D=/share/CACHEDEV1_DATA/.qpkg/container-station/bin/docker
cd /share/Container/workbuddy2api-hub

# Restore the previous exact production tag in .env.
# Current known-good rollback target:
# WB_IMAGE_TAG=v1.7.2.1
vi .env

$D compose pull wb-proxy
$D compose up -d --force-recreate
$D compose ps
curl -fsS http://127.0.0.1:8788/health
```

If the failed upgrade changed persistent-data format, stop first and restore the matching pre-upgrade `data/accounts` and `data/usage` snapshot before starting the older image. Image rollback alone is not evidence that a future data migration is reversible.
