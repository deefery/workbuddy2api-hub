# T-008 — Shared Docker Network for OpenMAIC / Sub2API Access

Status: PASS
Date: 2026-10-13

## Goal

Allow OpenMAIC and Sub2API to reach the WorkBuddy gateway by stable Docker DNS without routing through the NAS host IP, while keeping WorkBuddy2API independently deployable.

## Design

`wb-proxy` remains on its Compose-owned `workbuddy2api-hub_default` network and additionally joins the existing external network:

`sub2api_sub2api-network`

This mirrors the existing OpenMAIC topology: `openmaic-app` already joins its own networks plus `sub2api_sub2api-network`.

Internal endpoint:

`http://wb-proxy:8788/v1`

Existing LAN endpoint remains:

`http://192.168.31.13:8788/v1`

## Changes

`deploy/nas/docker-compose.yml` now declares:

- service networks: `default`, `sub2api`;
- external network alias `sub2api` -> `sub2api_sub2api-network`.

No WorkBuddy product code, credentials, ports, persistent mounts, image tag or release identity changed.

## Production safety

Before recreate, the current NAS Compose file was backed up to:

`/share/Container/workbuddy2api-hub/backups/network-coupling-20261013-012638/docker-compose.yml`

- `data/usage/usage.jsonl`: `6e97508c020f331e5156b68d24eff123c7a40019825a92170684135a3d905025`

## Acceptance evidence

After `wb-proxy` recreate:

- container health: `healthy`;
- own network: `workbuddy2api-hub_default`, IP `172.29.24.2`;
- shared network: `sub2api_sub2api-network`, IP `172.29.16.6`;
- `openmaic-app` Docker DNS resolves `wb-proxy` to `172.29.16.6` and `GET http://wb-proxy:8788/health` succeeds;
- `sub2api` Docker DNS resolves `wb-proxy` to `172.29.16.6` and the same health request succeeds;
- NAS/LAN health path remains successful;
- health response still reports `accounts: 2`, `accounts_ready: 2`, `api_key_required: true`;
- persistent settings and usage hashes are unchanged.

## Result

PASS. OpenMAIC/Sub2API can use stable internal service discovery while WorkBuddy2API retains an independent Compose lifecycle and its existing LAN port.
