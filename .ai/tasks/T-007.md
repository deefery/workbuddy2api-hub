# T-007 — Upstream Sync & Safe Auto-Deploy

Status: READY — implementation pending
Date: 2026-10-13

## Goal

Reduce normal fork maintenance to a safe one-click workflow when most changes come from upstream rather than from local product modifications.

## Intended operator entrypoints

- `Check-Upstream.cmd`: read-only upstream drift check and summary.
- `Update-From-Upstream.cmd`: explicit operator-triggered sync, validation, release and NAS update pipeline.
- Implementation should keep the real logic in a reviewable PowerShell script rather than embedding complex logic in `.cmd`.

## Required flow

1. Require a clean local workspace and known `origin` / `upstream` remotes.
2. Fetch `upstream` and `origin`.
3. Detect whether `upstream/main` contains new commits.
4. Keep `main` upstream-friendly and advance it only by a deliberate clean synchronization path.
5. Integrate the upstream delta into `custom/main` on an isolated sync branch/worktree.
6. Stop on non-trivial merge conflicts or release-workflow changes that require review.
7. Determine the upstream stable version and generate the fork version using the accepted dot-numeric rule, e.g. upstream `1.7.3` -> fork `1.7.3.1`.
8. Update all exact release identity points without weakening source/tag/package equality checks.
9. Run focused release-engineering tests and the full relevant test suite before any release mutation.
10. Push the reviewed integration state and exact release tag only after tests pass.
11. Preserve the existing draft-first GitHub release pipeline; do not bypass it.
12. Verify packaged assets, published Release, GHCR multi-arch image and immutable RepoDigest.
13. Before NAS mutation, snapshot `.env`, Compose and persistent `accounts` / `usage` state.
14. Update only the exact reviewed image tag, pull, recreate, verify digest and health.
15. Run a minimal real-state smoke: accounts ready and authenticated API request.
16. If the new container fails health, account readiness, digest verification or smoke, restore the previous exact image tag; if data format changed, stop and require matching data rollback rather than pretending image-only rollback is safe.

## Stop conditions

The updater must stop without touching production when any of these occur:

- dirty/unexpected local workspace;
- unexpected Git divergence or merge conflict;
- upstream changed release/version/packaging workflows in a way the updater does not understand;
- release identity cannot be determined exactly;
- tests fail;
- Draft Release/assets fail;
- GHCR publication/digest/platform verification fails;
- NAS preflight/snapshot fails.

After NAS mutation, unhealthy container, lost account readiness or failed API smoke must trigger rollback to the previous exact tag when state compatibility permits.

## Safety posture

- Initial version is **operator-triggered**, not an unattended auto-updater.
- A scheduled job may run `Check-Upstream.cmd`, but unattended production mutation is deferred until several real upstream upgrades prove the pipeline reliable.
- Never use moving `latest` as production identity.
- Never write credentials into Git, logs or generated reports.
- Keep `main` and `custom/main` roles from D-001/D-009 intact.

## Acceptance

- read-only check mode is idempotent and clearly reports no-update / update-available states;
- a synthetic or real clean upstream update can pass through sync/test/release staging without touching NAS before all pre-production gates pass;
- failure injection at each gate proves production is untouched or safely rolled back as appropriate;
- successful update records old/new upstream commit, fork version/tag, GHCR digest, NAS previous/new tag and final health;
- documentation describes manual recovery when automation stops.
